# 이력서/경력기술서 작성 가이드

목표: 개발자 이력서와 경력기술서를 일관된 톤으로 작성하기 위한 기준을 정의한다.

## 핵심 방향

- 문서는 과장된 자기소개보다 수행한 일, 해결한 문제, 만든 구조, 얻은 결과를 중심으로 쓴다.
- 이력서는 전체 경력의 요약과 신뢰 형성에 집중하고, 경력기술서는 프로젝트별 문제 해결 과정을 자세히 설명한다.
- 모든 문장은 채용 담당자와 기술 면접관이 빠르게 스캔할 수 있도록 짧고 명확하게 쓴다.
- 기술명은 원문 표기를 유지하고, 설명은 한국어로 풀어 쓴다.

## 문서별 역할

### 이력서

이력서는 후보자의 전체 경력, 전문 분야, 기술 역량, 주요 경력 이력을 빠르게 파악하게 하는 문서다.

권장 구성:

1. 문서 제목
2. 이름, 직무, 경력 연차
3. 연락처와 링크
4. 직무
5. 요약
6. 소개
7. 경력
8. 기술 역량
9. 학력
10. 자격/교육

작성 기준:

- 첫 화면에서 이름, 직무, 연차, 연락처가 바로 보이게 한다.
- 요약은 5-7개 문장으로 핵심 강점을 압축한다.
- 소개는 일하는 방식, 문제 해결 성향, 리딩 경험 등 사람과 협업 관점을 보완한다.
- 경력은 회사별로 기간, 포지션, 도메인, 담당업무, 사용기술을 반복한다.
- 기술 역량은 기술명만 나열하지 않고, 해당 기술로 무엇을 해봤는지 짧게 설명한다.

### 경력기술서

경력기술서는 프로젝트 단위로 문제 해결 역량과 기술적 기여를 증명하는 문서다.

권장 구성:

1. 문서 제목
2. 짧은 문서 소개 문장
3. 회사명과 기간
4. 프로젝트명
5. 기술 스택
6. 역할
7. 문제
8. 해결 / 기여
9. 결과

작성 기준:

- 회사 아래에 주요 프로젝트를 배치한다.
- 각 프로젝트는 기술 스택과 역할을 먼저 제시한다.
- 본문은 `문제 -> 해결 / 기여 -> 결과` 순서로 고정한다.
- 문제는 개인의 불만이 아니라 시스템, 운영, 데이터, 비용, 확장성 관점의 상태로 쓴다.
- 해결은 본인이 직접 설계, 구현, 정리, 도입, 개선한 행동 중심으로 쓴다.
- 결과는 운영 안정성, 비용 절감, 생산성 향상, 확장성 확보, 데이터 신뢰도 개선처럼 채용자가 평가할 수 있는 변화로 정리한다.

## 포맷 가이드

### 제목 체계

- 문서 최상단 제목은 문서의 목적이 바로 드러나게 간결하게 쓴다.
- 주요 섹션은 내용의 역할이 드러나는 명사형으로 쓴다.
- 경력기술서의 하위 섹션은 `문제`, `해결 / 기여`, `결과`처럼 고정된 구조를 유지한다.
- 프로젝트 제목은 번호와 프로젝트명을 함께 쓴다.

예시:

```md
## 회사명 (2023 - 현재)

### 1. 프로젝트명

- 기술 스택: NestJS(TypeScript), AWS, MongoDB
- 역할: 백엔드 아키텍처 설계 및 서비스 개발 주도

#### 문제

#### 해결 / 기여

#### 결과
```

### 항목 구조

회사 경력 항목:

```md
### 회사명 (YYYY. MM. - YYYY. MM.)

- 포지션: 백엔드 개발자
- 도메인: 커머스, 보안, AI 등
- 담당업무:
  - 무엇을 설계/구현/개선했는지 작성
  - 어떤 문제를 해결했는지 작성
  - 어떤 결과를 만들었는지 작성
- 사용기술: 기술명, 기술명, 기술명 등
```

프로젝트 항목:

```md
### 프로젝트명

- 기술 스택: 기술명, 기술명, 기술명
- 역할: 본인의 책임 범위

#### 문제

- 기존 상태의 한계나 병목을 작성한다.

#### 해결 / 기여

- 본인이 수행한 설계, 구현, 개선, 조율 내용을 작성한다.

#### 결과

- 개선된 상태와 확인 가능한 성과를 작성한다.
```

### 정보 밀도

- 회사별 담당업무는 4-8개 bullet로 정리한다.
- 경력기술서의 `문제`, `해결 / 기여`, `결과`는 각각 2-7개 bullet을 권장한다.
- 한 bullet은 가능하면 한 가지 기여만 담는다.
- 한 문장이 길어질 경우 쉼표를 늘리기보다 문장을 나눈다.
- 기술 스택은 본문에 흩뿌리지 말고 별도 줄에 모아 둔다.

## 말투 가이드

### 기본 문체

- 이력서 본문은 격식 있는 평서형을 사용한다.
- 경력기술서 bullet은 간결한 서술형을 사용한다.
- 자기평가보다 행동과 결과가 드러나는 동사를 사용한다.
- 감정적 표현, 과도한 수식어, 주관적 평가어를 피한다.

권장 어미:

- 이력서: `보유하고 있습니다`, `구축해왔습니다`, `개선했습니다`, `갖추고 있습니다`
- 경력기술서: `설계함`, `구축함`, `개선함`, `확보함`, `수행함`, `적용함`

사용하기 좋은 동사:

- 설계하다
- 구현하다
- 구축하다
- 개선하다
- 통합하다
- 분리하다
- 표준화하다
- 최적화하다
- 확보하다
- 주도하다
- 도입하다
- 운영하다
- 마이그레이션하다

피해야 할 표현:

- 열심히 했습니다
- 많은 것을 배웠습니다
- 다양한 업무를 했습니다
- 훌륭한 결과를 냈습니다
- 최고 수준의 역량을 가지고 있습니다
- 모든 것을 담당했습니다

대체 방식:

| 약한 표현 | 권장 표현 |
| --- | --- |
| 다양한 백엔드 업무를 했습니다 | 사용자, 결제, 리포트 도메인의 API 서버를 설계하고 구현했습니다 |
| 성능을 좋게 만들었습니다 | 비동기 워커 구조를 도입하여 장시간 작업 처리 안정성을 개선했습니다 |
| 팀워크를 잘했습니다 | API 스펙을 정의하고 프론트엔드 팀과 인터페이스를 조율했습니다 |
| 인프라를 관리했습니다 | ECS 기반 배포 구조를 재설계하고 CI/CD 파이프라인을 구축했습니다 |

## 표기 기준

### 원문 표기를 유지하는 항목

- 기술명과 제품명: `NestJS`, `TypeScript`, `AWS`, `Docker`, `GitHub Actions`
- 약어와 도메인 용어: `API`, `CI/CD`, `RAG`, `MCP`, `RBAC`, `POS`, `OKR`

### 한국어로 쓰는 항목

- 본문 설명
- 담당업무
- 문제 상황
- 해결 과정
- 결과
- 역할 설명
- 도메인 설명

### 혼합 표기 원칙

- 기술명은 공식 표기 그대로 쓰고 괄호로 보조 설명을 붙인다.
- 같은 기술은 문서 전체에서 같은 표기를 유지한다.
- 한글화가 어색한 기술 용어는 번역하지 않는다.
- 날짜는 `YYYY. MM. - YYYY. MM.` 또는 `YYYY - 현재` 형식으로 통일한다.

예시:

```md
- 기술 스택: NestJS(TypeScript), MongoDB, Redis, AWS(ECS, S3, CloudWatch)
- 역할: 백엔드 아키텍처 설계 및 서비스 전반 개발 주도
```

## 내용 작성 원칙

### 요약 작성법

요약은 다음 순서로 작성한다.

1. 총 경력과 주력 직무
2. 주력 기술과 아키텍처 강점
3. 핵심 도메인 경험
4. 인프라/운영 경험
5. 최신 기술 또는 차별화 경험
6. 리딩/프로세스/조직 운영 경험

템플릿:

```md
약 N년간 [주력 분야]를 중심으로 서비스를 설계·구축·운영해온 [직무]입니다.

[주요 기술] 기반 [시스템/API/아키텍처] 설계에 강점을 가지고 있습니다.

[도메인/핵심 시스템]을 직접 설계하고 개선해왔습니다.

[인프라/운영/비용 최적화] 경험을 보유하고 있습니다.

[LLM, 데이터, 보안 등 차별화 기술] 기반 시스템 개발 경험을 보유하고 있습니다.

[리딩/협업/프로세스]를 통해 지속 가능한 개발 문화를 구축해왔습니다.
```

### 소개 작성법

소개는 기술 스펙보다 일하는 방식을 설명한다.

포함할 내용:

- 어떤 기술 기반으로 서비스를 만들어왔는지
- 단순 기능 개발을 넘어 어떤 관점으로 개선하는지
- 팀 리딩이나 협업에서 중요하게 생각하는 기준
- 제약 조건 속에서 의사결정하는 방식

작성 톤:

- 자기소개이지만 감성적 문장보다 직업적 관점에 집중한다.
- "저는"을 반복하지 않는다.
- 추상적 가치관은 실제 행동과 연결한다.

### 경력 작성법

회사별 경력은 다음 정보를 반복한다.

- 회사명과 재직 기간
- 퇴사/종료 사유가 설명 가치가 있을 경우 한 줄로 작성
- 포지션
- 도메인
- 담당업무
- 사용기술

담당업무 작성 순서:

1. 가장 큰 책임 범위
2. 핵심 시스템 설계/구현
3. 데이터, 인프라, 운영 개선
4. 협업, 채용, 프로세스, 리딩
5. 정량 성과나 외부 인정

### 기술 역량 작성법

기술 스킬은 숙련도 점수보다 실무 맥락을 쓴다.

예시:

```md
### Backend

- NestJS: 모노레포 아키텍처 설계 및 API 서버 구축 경험
- Express.js: REST API 설계 및 레거시 시스템 개선 경험
- Bull Queue: 비동기 작업 처리 및 워커 시스템 구축
```

분류 기준:

- `Backend`
- `Infrastructure`
- `Database`
- `Frontend / Mobile`
- `AI / LLM`

## 경력기술서 작성 원칙

### 문제

문제는 "왜 이 일이 필요했는가"를 설명한다.

좋은 문제 서술:

- 기존 구조의 한계가 명확하다.
- 기술적/운영적 리스크가 드러난다.
- 본인의 기여가 필요한 이유가 보인다.

문제 범주:

- 레거시 아키텍처
- 데이터 구조 불일치
- 운영 비용 증가
- 배포 불안정
- 수작업 의존
- 시스템 간 데이터 단절
- 장시간 작업 처리 한계
- 권한/보안 구조 부재
- 팀 프로세스 미정립

템플릿:

```md
- 기존 [시스템/서비스]는 [문제 상태]로 인해 [운영/확장/신뢰성] 측면의 한계가 있었음.
- [작업/데이터/프로세스]가 표준화되어 있지 않아 [구체적 비용 또는 리스크]가 발생하고 있었음.
```

### 해결 / 기여

해결은 "내가 무엇을 했는가"를 설명한다.

좋은 해결 서술:

- 주어가 없어도 본인의 행동임이 분명하다.
- 설계, 구현, 도입, 개선, 조율 중 어떤 기여인지 명확하다.
- 기술 선택과 구조적 변화가 드러난다.

템플릿:

```md
- [기술/방식] 기반으로 [시스템/구조]를 설계하고 [효과]를 확보함.
- [데이터/서비스]를 [분리/통합/정리]하여 [일관성/확장성/유지보수성]을 개선함.
- [도구/프로세스]를 도입하여 [배포/협업/운영] 체계를 표준화함.
```

### 결과

결과는 "그래서 무엇이 달라졌는가"를 설명한다.

좋은 결과 서술:

- 가능하면 정량 수치가 포함된다.
- 수치가 없더라도 개선된 상태가 구체적이다.
- 기술적 결과와 비즈니스/운영 결과를 함께 보여준다.

결과 범주:

- 개발 생산성 개선
- 유지보수 효율 개선
- 배포 안정성 확보
- 운영 비용 절감
- 데이터 신뢰도 회복
- 시스템 확장성 확보
- 사용자 경험 개선
- 팀 협업 방식 표준화

템플릿:

```md
- [구조/시스템]을 구축하여 [운영/개발/사용자] 측면의 [효율성/안정성/확장성]을 개선함.
- [기능/프로세스]를 통해 [기존 상태]에서 [개선된 상태]로 전환함.
- [비용/시간/처리량/횟수] 기준으로 [정량 성과]를 달성함.
```

## 정량 표현 가이드

정량 지표는 신뢰도를 높인다. 다만 검증 가능한 숫자만 사용한다.

사용하기 좋은 지표:

- 비용 절감액 또는 절감률
- 확보한 크레딧/예산
- 처리량
- 배포 빈도
- 장애 복구 시간
- 교육/공유 세션 횟수
- 프로젝트 수
- 팀 규모
- 운영 기간

표현 예시:

```md
- AWS 크레딧 $N 확보 및 인프라 구조 정리를 통해 클라우드 비용을 최적화했습니다.
- 사내 기술 교육 프로그램을 N회 이상 운영하여 팀 내 기술 공유 체계를 정착시켰습니다.
- 월 서버 비용을 N원에서 N원 이하로 절감했습니다.
```

## 시각/문서 스타일

- 전체적으로 흰 배경, 어두운 남색 계열 본문, 초록 계열 포인트 컬러를 사용하는 차분한 기술 문서 스타일이 어울린다.
- 본문 가독성을 우선하고 장식 요소는 최소화한다.
- 폰트는 시스템 sans-serif 계열을 사용한다.
- heading과 bullet 중심의 문서형 레이아웃을 유지한다.
- 카드형 자기소개나 마케팅 문구보다 문서와 기술 블로그에 가까운 밀도를 유지한다.

권장 Markdown 습관:

- heading hierarchy를 엄격히 지킨다.
- 한 줄에 너무 많은 정보를 넣지 않는다.
- 같은 종류의 정보는 같은 순서로 반복한다.
- 기술 스택과 역할은 프로젝트 설명보다 먼저 둔다.
- 이미지나 수상 자료는 본문 흐름을 방해하지 않는 보조 증거로만 사용한다.

## 체크리스트

작성 후 아래 기준으로 검토한다.

- 이력서 첫 화면에서 직무, 경력, 연락처, 주력 기술이 보이는가?
- 요약이 경력 전체를 5-7문장으로 압축하는가?
- 회사별 경력 항목의 정보 순서가 일관적인가?
- 경력기술서가 모든 프로젝트에서 `문제 -> 해결 / 기여 -> 결과` 구조를 지키는가?
- 각 bullet이 하나의 기여 또는 하나의 결과만 말하는가?
- 기술명 표기가 문서 전체에서 일관적인가?
- "열심히", "다양한", "훌륭한" 같은 약한 표현을 제거했는가?
- 결과 항목에 개선된 상태나 정량 지표가 포함되어 있는가?
- 이력서와 경력기술서가 서로 중복되지 않고 요약/상세 역할을 나누는가?

## 최소 템플릿

### 이력서 템플릿

```md
# 이력서

이름 · 직무 (N년차)

- email@example.com
- github.com/example

## 직무

소프트웨어 개발 / 웹 백엔드 개발

## 요약

약 N년간 [분야]를 중심으로 서비스를 설계·구축·운영해온 [직무]입니다.

[주요 기술] 기반 [강점]을 보유하고 있습니다.

[핵심 시스템]을 직접 설계하고 개선해왔습니다.

[인프라/데이터/AI 등] 경험을 보유하고 있습니다.

[리딩/협업/프로세스] 경험을 통해 지속 가능한 개발 문화를 구축해왔습니다.

## 소개

[기술 기반]으로 다양한 도메인의 서비스를 설계·구축해왔습니다.

단순 기능 개발을 넘어 [성능/비용/운영/구조] 개선을 통해 서비스의 지속 가능성을 높이는 데 집중합니다.

[협업/리딩/의사결정] 측면에서 중요하게 생각하는 기준을 작성합니다.

## 경력

### 회사명 (YYYY. MM. - 현재)

- 포지션: [포지션]
- 도메인: [도메인]
- 담당업무:
  - [핵심 책임과 기여]
  - [시스템 설계/구현]
  - [운영/인프라/데이터 개선]
- 사용기술: [기술 목록]

## 기술 역량

### Backend

- [기술명]: [실무 경험 요약]
```

### 경력기술서 템플릿

```md
# 경력기술서

지금까지 수행한 주요 프로젝트와 해결한 문제, 사용한 기술, 기여 내용을 정리했습니다.

## 회사명 (YYYY - YYYY)

### 1. 프로젝트명

- 기술 스택: [기술 목록]
- 역할: [역할과 책임 범위]

#### 문제

- [기존 상태와 문제]
- [운영/기술/비즈니스 리스크]

#### 해결 / 기여

- [본인이 설계/구현/개선한 내용]
- [기술 선택 또는 구조 변경]
- [협업/운영/프로세스 개선]

#### 결과

- [개선된 상태]
- [정량 성과 또는 검증 가능한 변화]
```
